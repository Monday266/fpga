# 一、公司介绍

超威半导体公司（AMD，Advanced Micro Devices, Inc.）成立于1969年，总部位于美国加州圣克拉拉，是全球领先的半导体设计企业之一。公司专注于高性能计算、图形和可视化技术，产品涵盖桌面与服务器处理器、GPU显卡、加速计算平台等领域。凭借锐龙（Ryzen）、霄龙（EPYC）和镭龙（Radeon）等产品线，AMD在数据中心、高性能计算和个人PC市场持续扩大影响力。近年来，随着人工智能、大数据和云计算的发展，AMD不断加强在异构计算和高能效架构上的布局，成为全球芯片产业重要力量。

在FPGA与SoC领域，AMD于2022年完成对赛灵思（Xilinx）的收购，进一步扩展了自身的产品组合。AMD FPGA和自适应SoC广泛应用于数据中心、5G通信、汽车电子、工业控制等场景，能够满足灵活性和高性能并存的需求。其Versal自适应SoC系列将AI引擎、可编程逻辑与高效处理器结合，为智能边缘和高性能计算任务提供卓越支持；Alveo加速卡则面向数据中心和云应用，助力低延迟高吞吐的加速计算。通过整合CPU、GPU与FPGA的异构计算生态，AMD正推动从云到端的智能化应用发展，为新一代计算平台奠定基础。

## 2.1 AMD PYNQ-Z2 板（PYNQ-Z2 Board）

PYNQ-Z2 是一款基于 Zynq-7000 SoC 的开发板，定位于教育与初学者平台，支持通过 Python 和 Jupyter Notebook 控制 FPGA 与处理器资源。

- 器件为 Zynq-7000 XC7Z020，双 ARM Cortex-A9 处理器与可编程逻辑，可实现硬件加速与嵌入式系统开发。
- 利用 PYNQ 框架，开发者可使用 Python API 调用硬件逻辑（Overlay），无需深入硬件设计。
- 接口丰富：HDMI 输入/输出、以太网、USB、音频接口、Arduino 与 Raspberry Pi 扩展接口、Pmod 接口、LED 与按键等。
- 适合计算机视觉、信号处理、硬件教学、嵌入式实验等应用。
- 通常通过 micro-SD 卡启动，支持使用 Jupyter Notebook 进行远程控制和开发。
- 参考链接：https://pynq.readthedocs.io/en/latest/index.html

## 2.2 AMD Kria KR260 Robotics Starter Kit

KR260 是 Kria 系列中面向机器人与工业应用的开发套件，由 K26 SOM 与机器人载板组成，定位于高速视觉与实时数据传输。

- 基于 Zynq UltraScale+ MPSoC 架构的 K26 SOM，搭配 4GB DDR4 内存与主动散热方案。
- 网络接口：4 路 RJ45 千兆以太网，另有 SFP+ 笼可支持 10G Ethernet 高带宽视觉数据。
- 扩展接口：Raspberry Pi HAT 排针、4 个 Pmod 连接器、USB 3.0，以及面向高分辨率传感器的 SLVS-EC 接口。
- 原生支持 ROS 2 与 Kria Robotics Stack（KRS），也可使用 Vivado / Vitis 原生流程或 Kria-PYNQ。
- 适合机器人视觉、工业检测、高清巡检等高带宽实时场景。
- 参考链接：https://www.amd.com/en/products/system-on-modules/kria/k26/kr260-robotics-starter-kit.html
- 用户指南 UG1092：https://docs.amd.com/r/en-US/ug1092-kr260-starter-kit

## 2.3 SEA 板卡（Seeed Spartan Edge Accelerator Board）

SEA 板卡是 Seeed Studio 出品的 Arduino 扩展板形态 FPGA 板卡，定位于 IO 扩展与执行控制。

- 器件为 Spartan-7 XC7S15，12,800 个逻辑单元、2,000 个 slice、360 KB 片上 RAM。
- 板载 Espressif ESP32-D0WDQ6，提供 Wi-Fi 802.11 b/g/n 与 BLE 4.1 连接能力。
- 形态为 Arduino Shield 兼容（32-pin 排针），可直接叠装于 Arduino 主板之上。
- 视频与存储：Mini HDMI 输出、CSI/MIPI 摄像头接口（支持树莓派 Camera V1，OV5640）、Micro SD/TF 卡槽。
- 扩展与板载器件：10-pin FPGA GPIO 排针、2 个 Grove 接口（I2C 与 D2/D3）、8-bit ADC 与 DAC、六轴加速度计与陀螺仪 LSM6DS3TR、2 个单色 LED 与 2 个 RGB LED、Boot / Reset / User 按键。
- 供电方式：USB Type-C、VIN（8–17 V）或 Arduino 侧 micro USB。
- 电平注意事项**：SEA 扩展板的 IO 电平为 5 V，而 FPGA 侧 IO 为 3.3 V，因此只能与 5 V 电平的 Arduino 主板（如 Arduino UNO）配合使用。
- 参考链接：https://wiki.seeedstudio.com/Spartan-Edge-Accelerator-Board/

## 3.1 RTL/HLS 本地智能体设计赛道

### 3.1.1 赛道简介

近年来，大模型生成硬件代码的能力有所提升。现有公开评测结果主要反映模型在特定数据集和评价指标下的表现，与实际工程交付所要求的功能正确性、可综合性及约束收敛能力并不完全等同。除代码语言与语法能力外，工具反馈的利用方式、失败诊断与重试策略，以及模型外部领域知识的组织方式，也可能影响方案的工程表现。

模型参数量是影响结果的因素之一，但并非唯一因素。已有部分研究和评测表明，经过硬件领域专项训练或适配的较小模型，在特定任务上可能达到与更大规模通用模型相近或更好的表现。因此，在硬件设计任务中，除参数规模外，模型选择、知识组织与智能体设计也值得综合考虑。

基于上述背景，本赛道重点考察：**在一张消费级或工作站级 GPU 的算力与显存约束内，使用可本地部署的开源模型，并结合自行设计的智能体、领域知识以及 AMD Vivado / Vitis 工具链的编译、仿真、运行与综合反馈，能够在多大程度上提高硬件设计任务的通过率，以及由此产生的时间和计算成本。**

### 3.1.2 设计任务

参赛队伍提交一套可在指定环境中运行的完整方案，使其在给定的硬件设计题集上尽可能多地产出功能正确的代码。

**方案须包含**

| 组成 | 内容 |
| --- | --- |
| 模型 | 可本地部署的开源权重，须声明来源与版本 |
| 推理栈 | 推理后端及其服务配置 |
| 智能体 | 控制流、重试策略、上下文管理、工具编排 |
| 技能包 | 提示词模板、校验脚本、踩坑清单等领域知识的组织 |
| 基线入口 | 绕过智能体与技能包的单次直接生成脚本，供赛事方计量增益项 |

提交物为一个基于官方基础镜像构建的容器，该容器在断网沙箱中运行，自行完成从读题到产出代码的全过程。

**两个 track**

| Track | 目标语言 |
| --- | --- |
| RTL | Verilog / SystemVerilog |
| HLS | Vitis HLS C++ |

两个 track 独立排名、独立评奖，**推荐参赛队伍只选其一**；若两个都做，则在两个榜单上分别计分，最终排名取其中较高的一个。

**数据集**

开发阶段建议以下列公开数据集进行自测，并将实测结果写入设计报告：

| 数据集 | 适用 Track | 地址 |
| --- | --- | --- |
| VerilogEval v2 | RTL | https://github.com/NVlabs/verilog-eval （dataset_spec-to-rtl） |
| HLS-Eval | HLS | https://github.com/sharc-lab/HLS-Eval |

参赛队伍亦可自行补充其他数据集，其结果一并写入报告。

**评测阶段。** 赛事方另备一套**评测题集**，赛前不公开，于评测窗口分发给决赛入围队伍。

题集赛前不公开，方案在其上的表现构成泛化能力的真值。窗口内不得修改方案代码、技能包或模型权重，提交材料的哈希须与作品提交阶段的方案包一致；赛事方以队伍提交的容器与脚本抽查复现。评测题集的题量与构成于赛前公告。

**判定口径**

两个 track 均采用分级判定，逐级递进，只有通过前一级才进入下一级。**全部判定在 AMD Vivado / Vitis工具链上完成。**

| RTL：可编译 → 仿真通过 → 可综合 HLS：可解析 → 可编译 → 可运行（通过全部测试用例） → 可综合 |
| --- |

| RTL 级别 | 判定方式 |
| --- | --- |
| 可编译 | xvlog 分析与 xelab 详细描述通过 |
| 仿真通过 | xsim 运行参考测试台，与参考实现逐拍比对无差异 |
| 可综合 | 在xczu3eg-sbva484-1-e 上 synth_design 产出网表且无 ERROR |

**目标器件统一为 `xczu3eg-sbva484-1-e`，时钟约束 5 ns，RTL 与 HLS 两个 track 使用同一器件。** HLS 侧四级全部由 Vitis HLS 完成，两个 track 均同时报告 pass@1 与 pass@5。

## 3.2 具身智能赛道

### 3.2.1 赛道简介

具身智能系统需要在真实环境中完成感知、决策和执行。在机器人、智能制造、工业控制和边缘视觉等应用中，端侧 AI 负责判断，高速传感和实时控制负责把判断转成设备动作。这条链路的难点不在任何单一环节，而在于闭环：模型再准，若判断到动作之间的延迟不可控、抖动不可测，系统在物理世界中依然不可用。

本赛道要求参赛队伍使用 AMD AI PC 与 FPGA/Zynq 搭建异构协同的具身智能系统。AI PC 负责端侧感知与决策，FPGA/Zynq 负责实时控制和物理接口，两者共同完成一项真实的物理任务。

系统分工如下：

| 角色 | 职责 |
| --- | --- |
| Ryzen AI PC | 端侧 AI 推理、任务规划、人机交互、上层决策与系统调度 |
| AMD FPGA / Zynq 板卡 | 高速传感接入、实时处理、IO 扩展、运动控制、安全逻辑或低延迟数据桥接 |
| 两端协同 | 通信、数据流、时间同步与控制闭环，共同完成感知—理解—决策—控制—执行 |
| 可复用 Skill / Workflow | 将部署、硬件调用、模型推理、控制接口与调试方法封装为可迁移的能力（加分项） |

### 3.2.2 设计任务

参赛队伍自主选择应用场景，完成一套由 AI PC 与 FPGA/Zynq 协同实现的具身智能系统，并至少完成一项真实物理任务。

#### 3.2.2.1 核心命题

作品必须使用 AMD AI PC 作为上位机，运行端侧 AI 推理、任务决策、人机交互或系统调度。系统还必须包含 FPGA/Zynq 设计，用于高速传感接入、实时数据处理、IO 扩展、运动控制、安全逻辑或低延迟桥接。FPGA/Zynq 不能只用作普通 USB、串口或 GPIO 转接板。 队伍须说明其硬件功能和设计方法，并用演示或测试数据说明实际作用。机械结构可以简化，但 AI 决策到物理执行的闭环必须完整。

#### 3.2.2.2 选题方向

选题可以是以下方向之一，也可自行提出：

- 智能移动机器人导航与避障
- 视觉识别与自动分拣
- AI 机械臂抓取与控制
- 高清视觉检测与实时执行
- 多传感器融合与运动控制
- 人机交互驱动的智能执行系统
- 工业场景下的安全监测与实时控制

#### 3.2.2.3 必须完成的技术链路

### 3.2.4 优化目标与量化指标

#### 3.2.4.1 优化目标

- 提高任务闭环成功率，降低人工干预次数
- 压缩端到端响应延迟，尤其是 P95 / P99 与最大值，而非平均值
- 提高 FPGA/Zynq 在系统中的可量化贡献
- 降低控制周期抖动与截止期未命中率
- 在满足性能与时序的前提下合理使用片上资源
- 将部署、调试与硬件调用经验提炼为他人可复用的 Skill 或工作流

#### 3.2.4.2 指标报告口径

每个技术评分项至少要有一项可复测数据。作品必须报告五类核心指标：任务闭环成功率、端到端响应延迟、AI 任务效果和推理性能、FPGA/Zynq 的量化贡献，以及 AI PC 与 FPGA/Zynq 的通信性能。再按场景补充**至少两项**指标，可从视觉、控制、吞吐、可靠性、功耗或复用中选择。

#### 3.2.4.3 核心必报指标

| 指标 | 口径 |
| --- | --- |
| 任务闭环成功率 | 完整任务的成功次数除以有效测试总次数。测试前需定义成功、失败和人工干预，并说明测试次数 |
| 端到端响应延迟 | 从传感器产生数据或完成采集，到执行器产生实际物理响应的时间。需说明测量起点和终点，并报告 P50、P95、P99 和最大值，不能只给平均值 |
| AI 任务效果与推理性能 | 按场景选用效果指标：分类用 Accuracy 或 Macro-F1，目标检测用 mAP@0.5:0.95，分割用 mIoU，导航报告到达率、碰撞率或路径效率。推理延迟原则上按单样本（batch=1）测量，分别列出预处理、模型推理、后处理和总感知延迟；持续性能可用 FPS、samples/s 或 tokens/s 表示 |
| FPGA/Zynq 可量化贡献 | 报告 FPGA/Zynq 承担的功能在系统中的实测数据，如处理延迟、持续吞吐率、控制抖动、CPU 占用或系统功耗，并说明其功能为何不能由普通转接板或软件方案替代 |
| AI PC 与 FPGA/Zynq 通信性能 | 按通信方式报告单向延迟或 RTT，并选择有效吞吐率、丢包率、错误率、重传率或指令超时率。单向延迟需说明时钟同步方法；高速通道报告持续有效吞吐率，不以理论带宽代替实测结果 |

#### 3.2.4.4 场景专项指标（至少选报两项）

- 实时控制**：目标和实际控制周期、P99 抖动、截止期未命中率（Deadline Miss Rate）、跟踪均方根误差（RMSE）、超调量、调节时间和稳态误差
- FPGA 数据处理**：输入到输出的处理延迟、像素率、帧率、持续吞吐率，以及目标时钟、时序收敛状态和最差负裕量（WNS）
- FPGA 资源使用**：LUT、FF、BRAM、DSP 和片上存储使用率。资源使用率不是越高越好，应结合性能、时序和扩展余量判断设计是否合理
- 视觉与传感**：图像处理帧率、丢帧率、多传感器时间同步误差和数据完整率
- 系统可靠性**：连续稳定运行时间、异常次数、人工干预次数、故障恢复时间和安全状态触发成功率
- 功耗与能效**：空闲功耗、负载平均功耗、峰值功耗和单任务能耗。应说明测量范围是整机、AI PC、FPGA/Zynq 板卡还是外部执行机构
- Skill 与工作流复用**：在干净环境中的部署成功率和部署时间，以及在第二种设备或应用场景中的复用结果

#### 3.2.4.5 测试与证据要求

- 每项指标需注明具体硬件型号、模型及数值精度、输入规格、软件版本、FPGA 时钟频率、测试次数、测试时长和功耗模式
- 性能对比必须采用相同测试条件，并提供原始日志、测试脚本、逻辑分析仪或示波器结果等证据
- 延迟和抖动需报告分位数和最大值；吞吐与稳定性采用持续运行结果，不以瞬时峰值代替
- 不设统一的绝对性能门槛。评分结合任务难度、平台条件与设计目标综合判断

## 3.3 自主选题赛道（分初级组与高级组）

### 3.3.1 赛道简介

本赛道面向完整的 FPGA 作品，对器件、实现方式与应用领域均不作限定。参赛队伍自由选择题目，综合运用逻辑设计、状态机、时序约束、接口协议与软硬件协同等能力，完成一件可复现、可演示的作品。

#### 3.3.1.1 组别划分

本赛道按队员学历分为初级组与高级组，两组独立排名、独立评奖。

| 组别 | 参赛资格 | 器件范围 | 考察侧重 |
| --- | --- | --- | --- |
| 初级组 | 大学一年级至三年级在读本科生 | AMD FPGA 与 Zynq 器件 | 逻辑设计、状态机、时序约束、接口协议等基本 FPGA 设计能力 |
| 高级组 | 大学四年级本科生及在读硕士生、博士生 | AMD FPGA、Zynq 与 Versal 器件，无逻辑资源限制 | 在上述基础上进一步考察软硬件协同与器件整体性能的发挥 |

队伍中如同时含不同年级或学历的队员，按其中最高者归入高级组。报名后台有学生证与学历审核流程，违规报名将取消参赛资格。

两组的设计任务、提交内容与评测指标一致，仅在参赛资格、器件范围与考察侧重上有所区别。下文如无特别说明，各项要求对两组同时适用。

### 3.3.2 设计任务

参赛队伍自主选择应用方向与实现方式，完成一件完整的 FPGA 作品。

**选题要求**

- 应用方向不限。鼓励从 FPGA 之外的学科中寻找题目，也接受面向传统信号处理、通信、控制、图像与嵌入式系统的选题
- 鼓励综合考虑软硬件协同，充分发挥器件整体性能
**实现方式**

不作限定。RTL、Vitis HLS、AI Engine、PS 侧软件及其任意组合均可。作品的核心价值可以体现在硬件加速、系统集成、接口设计或应用创新中的任意一项或多项。

**初级组推荐方向：PYNQ**

初级组不限定实现方式，但推荐使用 PYNQ 框架完成作品：PS 侧用 Python 与 Jupyter Notebook 组织算法与数据流，PL 侧以 HLS 或 RTL 实现计算核心并封装为 Overlay，可以把精力集中在软硬件划分与硬件设计本身，而不必先跨过嵌入式软件栈的门槛。

在此基础上，**若能提炼出通用性较高的 PYNQ Skill，将在评分中加分**。这里的通用性指该 Skill 不与本队题目绑定，换一个题目、换一块板卡仍然可用，例如：

- 通用的 Overlay 加载与校验流程、寄存器映射与 register_map 使用范式
- 可复用的 DMA 搬运与缓存一致性处理封装，含常见出错情形的定位方法
- 从接口契约自动生成主机侧调用代码或测试骨架的脚本
- 黄金参考比对、性能与资源数据自动采集并生成报告的工具
Skill 的提交方式与评价标准见 3.3.5.2。从本队作品的开发过程中沉淀即可，但须写清它在本队题目之外还能用在哪类场景。高级组同样可以提交 PYNQ Skill，评价标准一致。

**考察重点**

作品的完整性与工程水平：功能是否正确、设计是否经过实测验证、性能与资源数据是否真实完整、他人能否复现。在此基础上，选题的创新性与应用价值占最高权重。

### 3.3.3 设计与优化要求

#### 3.3.3.1 工具限制

- 工具版本：Vivado / Vitis 2026.1（推荐）或 2025.2。如使用其他版本需在报告中说明并保证脚本可复现
- 允许使用任意公开大模型、微调后的本地模型，以及基于大模型构建的智能体应用。**须提交体现大模型协作过程的交互记录**，含提示词、模型回答与自我纠错轨迹
- 须将协作过程中沉淀的可复用经验提炼为技能包（Skill）**，随作品一并提交，见 3.3.5.2

#### 3.3.3.2 板卡与器件限制

- 初级组**：任意 AMD FPGA 或 Zynq 器件
- 高级组**：任意 AMD FPGA、Zynq 或 Versal 器件，不设逻辑资源限制
两组均须在提交物中声明具体型号，并应选择自身可实际获取并完成板级验证的器件。

作品须在板上跑通并提供实测输出。

#### 3.3.3.3 开源要求

所有提交作品在 GitHub 或 Gitee 上开源，采用允许再分发的开源协议，推荐 MIT 或 Apache-2.0。

### 3.3.4 优化目标

- 在目标器件上取得可测量的性能表现，并给出与基线的对比
- 合理使用片上资源，避免以显著的资源代价换取有限的性能收益
- 保证工程可由他人从零复现
- 将设计过程中的判断依据写进报告，而不只是呈现结果
- 将与大模型协作中获得的经验提炼为他人可复用的技能包

### 3.3.5 提交内容

#### 3.3.5.1 工程包

- 完整的工程文件与源码（RTL、HLS、PS 侧软件等，按实际采用的实现方式提交）
- 仿真或验证结果，说明功能正确性是如何确认的
- 综合与实现报告，含资源占用、时钟频率与关键性能指标
- 上板工程、运行脚本、实测输出与参考结果的比对数据
- 可复现的构建脚本

#### 3.3.5.2 技能包

置于 skill/ 目录，含 README.md 说明每一项的适用范围、使用方法与失效条件。技能包是把与大模型协作过程中沉淀下来的经验显式提炼出来，供他人直接复用，可以是以下任意一种或多种：

- 提示词工作流**：一组经过验证、能稳定完成某类任务的提示词模板及使用说明，例如从算法描述推导软硬件划分、根据综合报告定位瓶颈
- 案例模板**：可被下一个题目直接套用的工程骨架、脚本模板、报告模板
- 校验脚本**：自动比对黄金参考、检查资源与时序、验证工程可复现性的脚本
- 踩坑清单**：结构化整理的常见错误与定位方法，含触发条件与排查步骤
评价标准是可复用性：一支陌生队伍拿到该目录，能否直接用在自己的题目上。每一项须写明适用场景、使用方法与已验证的效果，并说明是从哪些失败或观察中总结得出。

**通用 PYNQ Skill 单独加分。** 若提交的 Skill 面向 PYNQ 框架且不与本队题目绑定（换题目、换板卡仍可用），在本赛道评分中另行加分，见 3.3.2。

#### 3.3.5.3 设计报告

- 选题背景与创新点：为什么选这个题目，它解决了什么实际问题，前人做过什么
- 设计原理与功能框图
- 软硬件划分依据与接口设计
- 优化过程，含优化前后的性能与资源对比表
- 大模型协作记录**：提示词、模型回答、自我纠错轨迹、智能体工作流设计（如有）
- 技能包的提炼过程**：从哪些失败或观察中总结、如何验证有效、边界如何确定
- 复现说明：一份可供他人从零开始完整执行的操作步骤

#### 3.3.5.4 推荐目录结构

仓库内所有目录名与文件名须使用纯英文（小写字母、数字、下划线或连字符），不得出现中文、空格或特殊字符，以保证跨平台复现与脚本自动化。中文只出现在文件的正文内容中。

| <project_name>/ ├── README.md # 项目简介 + 复现步骤 ├── src/ # 设计源码（RTL / HLS / PS 侧软件） ├── sim/ # 仿真或验证脚本与结果 ├── build/ # 可复现的构建脚本 + 综合与实现报告 ├── board/ # 上板工程、运行脚本与实测输出 ├── data/ # 测试数据与参考结果 ├── skill/ # 技能包 │ └── README.md └── report/ # 设计报告 + 大模型协作记录 |
| --- |

上表为推荐结构，非强制。采用其他组织方式的队伍须在 README.md 中给出目录对照说明。
