# RTL/HLS 本地智能体设计赛道

> 本文摘自《FPGA 创新设计赛道选题指南（AMD）》第三节，为便于按赛道查阅而拆分。
> 完整指南见仓库根目录的 [TRACK_GUIDE_2026.md](../../TRACK_GUIDE_2026.md)，
> 两者内容一致；如有出入，以完整指南与大赛官方公告为准。

## 赛道简介

近年来，大模型生成硬件代码的能力有所提升。现有公开评测结果主要反映模型在特定数据集和评价指标下的表现，与实际工程交付所要求的功能正确性、可综合性及约束收敛能力并不完全等同。除代码语言与语法能力外，工具反馈的利用方式、失败诊断与重试策略，以及模型外部领域知识的组织方式，也可能影响方案的工程表现。

模型参数量是影响结果的因素之一，但并非唯一因素。已有部分研究和评测表明，经过硬件领域专项训练或适配的较小模型，在特定任务上可能达到与更大规模通用模型相近或更好的表现。因此，在硬件设计任务中，除参数规模外，模型选择、知识组织与智能体设计也值得综合考虑。

基于上述背景，本赛道重点考察：**在一张消费级或工作站级 GPU 的算力与显存约束内，使用可本地部署的开源模型，并结合自行设计的智能体、领域知识以及 AMD Vivado / Vitis 工具链的编译、仿真、运行与综合反馈，能够在多大程度上提高硬件设计任务的通过率，以及由此产生的时间和计算成本。**

## 设计任务

参赛队伍提交一套可在指定环境中运行的完整方案，使其在给定的硬件设计题集上尽可能多地产出功能正确的代码。

**方案须包含**

| 组成 | 内容 |
| --- | --- |
| 模型 | 可本地部署的开源权重，须声明来源与版本 |
| 推理栈 | 推理后端及其服务配置 |
| 智能体 | 控制流、重试策略、上下文管理、工具编排 |
| 技能包 | 提示词模板、校验脚本、踩坑清单等领域知识的组织 |
| 基线入口 | 绕过智能体与技能包的单次直接生成脚本，供赛事方计量增益项 |

提交物为一个基于官方基础镜像构建的容器，该容器在断网沙箱中运行，自行完成从读题到产出代码的全过程。

**两个 track**

| Track | 目标语言 |
| --- | --- |
| RTL | Verilog / SystemVerilog |
| HLS | Vitis HLS C++ |

两个 track 独立排名、独立评奖，**推荐参赛队伍只选其一**；若两个都做，则在两个榜单上分别计分，最终排名取其中较高的一个。

**数据集**

开发阶段建议以下列公开数据集进行自测，并将实测结果写入设计报告：

| 数据集 | 适用 Track | 地址 |
| --- | --- | --- |
| VerilogEval v2 | RTL | https://github.com/NVlabs/verilog-eval （dataset_spec-to-rtl） |
| HLS-Eval | HLS | https://github.com/sharc-lab/HLS-Eval |

参赛队伍亦可自行补充其他数据集，其结果一并写入报告。

**评测阶段。** 赛事方另备一套**评测题集**，赛前不公开，于评测窗口分发给决赛入围队伍。

题集赛前不公开，方案在其上的表现构成泛化能力的真值。窗口内不得修改方案代码、技能包或模型权重，提交材料的哈希须与作品提交阶段的方案包一致；赛事方以队伍提交的容器与脚本抽查复现。评测题集的题量与构成于赛前公告。

**判定口径**

两个 track 均采用分级判定，逐级递进，只有通过前一级才进入下一级。**全部判定在 AMD Vivado / Vitis工具链上完成。**

| RTL：可编译 → 仿真通过 → 可综合 HLS：可解析 → 可编译 → 可运行（通过全部测试用例） → 可综合 |
| --- |

| RTL 级别 | 判定方式 |
| --- | --- |
| 可编译 | xvlog 分析与 xelab 详细描述通过 |
| 仿真通过 | xsim 运行参考测试台，与参考实现逐拍比对无差异 |
| 可综合 | 在xczu3eg-sbva484-1-e 上 synth_design 产出网表且无 ERROR |

**目标器件统一为 `xczu3eg-sbva484-1-e`，时钟约束 5 ns，RTL 与 HLS 两个 track 使用同一器件。** HLS 侧四级全部由 Vitis HLS 完成，两个 track 均同时报告 pass@1 与 pass@5。

## 设计与优化要求

### 测试环境

**开发阶段不限平台。** 参赛队伍可使用任何可获取的算力完成开发与迭代，赛事方不作限制也不提供配额。

**验证阶段提供 ROCm 验证平台，供队伍确认方案可在赛事方环境中运行，建议尽早完成一次跑通验证。**

- 模型须能在单张 32 GB 卡上完整容纳，不允许跨卡。** 不设参数量上限，改以显存为约束。**参数量与显存占用并不等价**，作为参照：32B 级模型须经 4-bit 量化方可容纳（约 18 GB），FP16 下约需 64 GB 而装不下；7B 级模型可直接使用 FP16（约 14 GB）。
- 上下文长度不作统一约束**，由参赛队伍自定，但须在 MODEL.md 与设计报告中如实声明。
- 云资源经 AMD 中国开发者平台申请，配额另行公告。本赛道具体的验证窗口和测评窗口时间点将另行公告。
- 已自行具备 ROCm 环境的队伍可不使用赛事方云资源，但仍须提交可在赛事方环境中重建的容器与脚本。

### 固定与开放的部分

|  | 内容 |
| --- | --- |
| 赛事方固定 | 基础镜像与 EDA 工具链（只提供 Vivado / Vitis，不含第三方工具）、题集与评分器、显存与时间预算 |
| 队伍自主 | 模型选择与量化、推理后端与服务参数、上下文长度与单次输出上限、智能体全部设计、技能包与提示词、是否微调 |

### 微调与专用模型

允许微调，微调后的权重须开源并在提交物中声明，赛事方不提供训练算力；亦允许直接使用已有的硬件专用开源模型，但须在 MODEL.md 中声明其来源与版本。

## 优化目标

- 提高评测题集上分级判定的通过率，尤其是「可综合」这一末级
- 缩小 pass@1 与 pass@5 的差值，即提升方案稳定性
- 提升相对同模型裸跑基线的增益幅度
- 降低单题与总墙钟时间
- 将失败诊断经验提炼为他人可复用的技能包

## 提交内容

### 方案包 (参考)

| <team_name>-agent/ ├── Dockerfile # 基于官方基础镜像构建 ├── model/ │ └── MODEL.md # 模型来源、版本、量化方式、显存占用、上下文配置 ├── agent/ # 智能体源码 ├── skill/ # 技能包 ├── serve/ # 推理服务配置与启动脚本 ├── run.sh # 单题入口：读题 → 产出代码 ├── run_baseline.sh # 基线入口：同一推理服务，绕过智能体与技能包 └── REPORT.md # 设计报告 |
| --- |

### 基线入口

run_baseline.sh 与 run.sh 使用同一推理服务与同一上下文配置，但绕过智能体与技能包，提示词仅含题目本身，单次生成、不重试、不调用工具。其结果作为增益项的基线，须与 run.sh 在同一次运行中产出。

### 模型声明

MODEL.md 中须写明模型来源（仓库地址与版本号，或权重文件的校验和）、量化方式、实测显存占用与上下文配置，若经微调，须补充基座模型、微调方式、训练数据来源与微调权重的开源地址。

### 设计报告

- 方案总体架构与设计依据
- 模型选择的理由，包括曾评估过并放弃的候选及原因
- 智能体设计：控制流、重试与回退策略、上下文管理方式
- 技能包的提炼过程：从哪些失败中总结、如何验证有效
- 在所选数据集上的实测结果
- 失败分析**：哪一类题目仍然做不出来，原因是什么
- 复现说明

### 评测指标与权重

| 评测项 | 权重 |
| --- | --- |
| 能力：题集加权通过率 | 30 |
| 增益：相对同模型裸跑基线的提升 | 40 |
| 代价：墙钟效率 | 10 |
| 智能体与技能包的工程质量 | 20 |
| 合计 | 100 |

注：提交内容的方案包，评分公式、判定阈值与各项预算的具体数值以后续分享的本赛道《评分细则》为准。
