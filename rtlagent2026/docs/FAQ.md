# 常见问题

---

## 参赛与环境

**Q1：不具备 GPU 条件能否参赛？**

开发阶段可以。本仓库的示范方案支持任意 OpenAI 兼容的商用 API，队伍自备 key 即可运行，
无需本地 GPU。

正式提交则须为本地部署的开源权重。决赛在断网沙箱中运行，容器无法连接任何外部服务。
验证阶段赛事方将开放云资源，经 AMD 中国开发者平台申请，配额另行公告。

**Q2：开发阶段使用商用 API、临近提交再更换为本地模型是否可行？**

技术上可行，但存在较大风险。商用 API 与本地小模型在输出长度、指令遵循与代码格式稳定性
上差异明显，围绕前者调校的提示词与重试策略，更换到后者之后往往不再适用。

较为稳妥的做法是尽早在本地模型上完成一次完整运行，规模较小亦可，以商用 API 摸清任务
形态，以本地模型确认方案成立。

**Q3：不具备 AMD 显卡与服务器时如何安装 Vivado？**

Vivado 的安装由队伍自行完成，本仓库不提供安装指导。`selftest/` 仅负责定位队伍已安装的
Vivado 并调用，定位失败时明确报错，不会在缺少工具的情况下给出判定结果。

判定所用的仿真与综合不依赖 GPU，亦不要求 AMD 显卡，Vivado 在通用 x86 CPU 上即可运行。
目标器件 `xczu3eg-sbva484-1-e` 属于免费档的器件支持范围，无需专业版 license。

**Q4：能否使用 iverilog 或 Verilator 进行本地自测？**

不建议，本仓库亦不提供该路径。赛事方全流程仅使用 AMD 工具链，本地改用其他仿真器将得到
不一致的判定结果，而不一致的判定较之没有判定更为不利，容易使队伍误认为某类问题已经解决。

`xvlog` 与 iverilog 的差异有实测依据：VerilogEval 的 156 个测试台在 iverilog 下全部可用，
在 `xvlog` 下则无一通过编译，原因参见 `selftest/README.md`。

**Q5：Windows 环境下脚本能否运行？**

本仓库以 Linux 环境为默认前提。Windows 用户建议在 WSL2 中使用，相关脚本未在原生
Windows 环境下验证。

**Q6：目标器件为何选用容量较小的 ZU3EG？**

该器件属于 Vivado 免费档的器件支持范围，队伍与赛事方均无需专业版 license。

器件容量不影响判定结果。VerilogEval v2 的 156 题在 ZU3EG 与更大器件上的分级判定逐题
一致，其中规模最大的设计仅占用 ZU3EG 的 LUT 容量 2.5%，全集未使用 DSP 与 BRAM。

## 题集与判定

**Q7：评测题集为何不予公开？**

VerilogEval 的 156 道题及其参考实现在网络上公开可得，且较大概率已包含于模型的训练语料
之中。题集一经分发即不再具备未见过的性质，而方案在未见题集上的表现才构成泛化能力的真值。

开发阶段建议以 VerilogEval v2 自测，并将实测结果写入设计报告。

**Q8：参考测试台是否提供给参赛智能体？**

不提供。判定 L2 所用的测试台由赛事方掌握，该测试台同时例化参考实现与被测模块并逐拍比对。
参赛智能体仅能获得题面（`prompt`）与模块声明（`interface`）。

如需在生成过程中进行自我验证，须由队伍自行编写测试台。在无法获得参考实现的前提下判断
生成结果是否正确，属于本赛道拟考察的工程问题之一，并非材料上的疏漏，其对应系数为 0.5，
为分级表中跨度最大的一级。

**Q9：L1 至 L2 的分差为何为 0.5，而 L2 至 L3 仅为 0.3？**

L1 到 L2 对应从代码通过工具到行为与参考实现一致，为本 track 中难度最高的一步。L2 到 L3
的跨度则小得多，逐拍比对通过的设计多数已经可综合，其余失败集中于少数不可综合构造。

**Q10：端口名称书写错误会产生何种后果？**

该题计为 L0。参考测试台按具名端口例化被测模块（`.q(q_dut)`），端口改名即等同于缺少一个
端口，`xelab` 详细描述随即失败：

```
ERROR: [VRFC 10-3180] cannot find port 'q' on this module
```

模块名称书写错误同理：

```
ERROR: [VRFC 10-2063] Module <TopModule> not found while processing module instance <dut1>
```

此类错误的代价高于功能实现错误，后者至少可得 L1 的 0.2 分。该规则与软件开发中的一般
经验不同，建议在提示词与技能包中专门处理。示范方案中的 `check_interface()` 即用于此，
以纯文本比较实现，不依赖任何工具。

**Q11：在输出端口上添加 `reg` 是否属于改动接口？**

不属于。`wire`、`reg` 与 `logic` 不构成契约的组成部分，不影响详细描述。将 `output q`
写作 `output reg q` 合法，且在由 `always` 块驱动时通常为必需。

接口契约的组成部分为模块名、端口名、方向与位宽。

**Q12：以 pass@1 而非 pass@5 计分，对稳定性较弱的方案是否构成不公平？**

pass@1 对应实际使用场景。若按 pass@5 计分，将激励以重复采样换取分数，而重复采样的代价
已由墙钟项另行计量，两者叠加会造成重复惩罚或重复奖励。

pass@5 与 pass@1 的差值具有诊断价值，因此单独列出，但不计入总分。

## 模型与方案

**Q13：为何不限制模型参数量？**

参数量难以核查，而显存占用可直接实测。决赛环境单卡显存为 32 GB，超出者无法运行。

参数量与显存占用并不等价：32B 模型在 FP16 下约需 64 GB，无法装载；经 4-bit 量化后约为
18 GB，可以运行；7B 模型在 FP16 下约需 14 GB，可直接使用。在同等显存条件下如何在参数量
与量化精度之间取舍，属于本赛道考察的工程判断之一。

**Q14：选用能力更强的模型是否即可获得高分？**

绝对通过率会相应提高，反映于能力项 30 分；但增益项 40 分以该模型的裸跑结果为基线，模型
越强则基线越高、增益越难做大。总分为两者的合成结果。

**Q15：能否使用他人已完成微调的硬件专用模型？**

可以，但须在 `MODEL.md` 中声明来源与版本。此类模型公开可得，各队伍均可取用，不构成不
公平。

需要注意的是，增益项以所选模型的裸跑结果为基线，因此选用更强的模型不会直接转化为更高
的总分。

**Q16：技能包是否必须涉及大模型？**

不作要求。技能包的评价标准在于他人能否复用，与是否调用模型无关。

示范方案中的 `check_interface()` 即为一例，该函数以纯文本方式比较模块头，不调用模型亦
不调用工具，却覆盖了整个 L0 失败类。确定性的校验脚本与结构化的踩坑清单同样计分。

**Q17：以确定性脚本完成接口检查与语法预检，是否属于绕过模型？**

不属于。此类工作本就应当由脚本承担，亦属技能包应有的内容。

判别界线在于产出的设计本身是否由模型生成。以脚本检查模型的输出属于工程实现；以脚本拼接
答案而模型调用不具实质作用，方为评分细则 2.9 所列的第三类情形。

**Q18：`run_baseline.sh` 需要绕过哪些环节？**

须绕过智能体与技能包：提示词仅包含题目本身，单次生成，不重试，不调用工具。

不绕过的部分为推理服务，即同一模型、同一量化方式与同一份上下文配置。基线与方案须在同一
次运行中产出，不接受分次提交，否则增益项的分子与分母不出自同一环境，其比值不具备意义。

## 评测执行

**Q19：单题超时如何处理？**

该题按 L0 计。设置墙钟上限的目的在于防止以无限重试换取通过率。

参赛服务应在 `deadline_s` 之前自行停止并返回当前的最好结果，即使为空字符串亦可，而不宜
由赛事方侧触发超时。前者仍存在获得 L1 的可能，后者则计为 L0。

**Q20：服务中途中断后能否重启？**

评测期间不予重启，失败即计为 L0，赛事方不再重投。请在投题前完成健康检查，并确保服务能够
连续处理数百次请求。

**Q21：为何采用墙钟时间而非 token 数计量？**

token 数产生于容器内部，容器外无法可靠观测；且同一模型在不同推理后端下的吞吐可相差数倍，
而后端选择、批处理与 KV cache 管理的调校本身即属本赛道应当考察的工程能力。

**Q22：同时参加两个 track 是否加分？**

不加分。两个 track 独立排名、独立评奖，不作合并计分，最终排名取其中较高者。

建议仅选择其一。两侧的工具链与失败模式差异较大，RTL 侧的主要瓶颈在于语义正确性与时序
语义，HLS 侧则在于可综合性约束与 pragma 作用域。要求两者兼做会明显提高门槛，而对区分度
并无助益。

## 合规

**Q23：哪些行为构成作弊？**

包括以下三类：

- 联网检索。沙箱断网，出流量非零即视为异常
- 硬编码答案。将答案预置于技能包或智能体代码之中
- 绕过模型。以确定性脚本产出结果，模型调用不具实质作用

判定依据为网络出流量、GPU 利用率曲线以及产物与 `trace.jsonl` 的一致性三项，任一项异常
即进入人工复核。经查实者，该 track 成绩作废。

**Q24：智能体中内置固定代码模板是否属于硬编码？**

不属于。提示词模板、代码骨架以及常见的 FSM 写法与复位写法均属正常的技能包内容，本赛道
鼓励此类沉淀。

判别界线在于相关内容是针对某一类问题的通用方法，还是针对某一道具体题目的答案。前者属于
技能，后者属于硬编码。

**Q25：能否使用 Claude Code、Cursor 等工具辅助开发智能体代码？**

可以。本赛道限制的是方案运行时须使用本地开源模型，对开发过程中所用工具不作限制。

按大赛统一要求，须提交大模型协作记录。
