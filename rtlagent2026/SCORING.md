# RTL track 评分细则

本文只规定评分口径与提交条件。任务形式、开放范围与环境说明见赛道说明文档与本仓库
[README.md](./README.md)。

HLS track 的口径与本文大同小异，但分级与系数不同，参见其各自仓库。

---

## 1. 概述

参赛队伍提交一套可本地部署的完整方案（模型、推理栈、智能体、技能包），在断网沙箱中
自行完成从读题到产出 Verilog / SystemVerilog 代码的全过程。

### 1.1 目标平台

|              | 验证阶段              | 决赛                |
| ------------ | --------------------- | ------------------- |
| 硬件         | Radeon PRO W7900 单卡 | Radeon AI PRO R9700 |
| 架构         | RDNA 3 / gfx1100      | RDNA 4 / gfx1201    |
| 显存约束     | **按单卡 32 GB 设计** | 单卡 32 GB，不跨卡  |
| EDA 工具     | Vivado 2026.1         | 同左                |
| 判定器件     | `xczu3eg-sbva484-1-e`，时钟 5 ns | 同左     |

开发阶段不限平台，队伍可自备算力；验证阶段开放赛事方云资源，用于在 ROCm 上验证方案
可运行。

**成绩以决赛环境的运行结果为准。** 判定器件仅用于 RTL 综合，与推理所用的 GPU 无关。

验证阶段与评测窗口的具体时间另行公告，见 http://www.fpgachina.cn/ 。

### 1.2 评分构成

| 评测项   | 权重 |
| -------- | ---: |
| 能力     |   30 |
| 增益     |   40 |
| 代价     |   10 |
| 工程质量 |   20 |
| 合计     |  100 |

前三项由运行数据直接算出，第四项含人工评定成分。

### 1.3 预算

| 项                                  | 值                                                           |
| ----------------------------------- | ------------------------------------------------------------ |
| 单卡显存                            | 32 GB                                                        |
| 单题墙钟上限                        | 赛前公告                                                     |
| 全题集墙钟上限                      | 赛前公告                                                     |
| 上下文长度、单次输出上限、RoPE 外推 | **不作统一约束**，由队伍自定，须在 `MODEL.md` 与报告中声明 |

预算由沙箱强制执行，超出单题墙钟上限的题目按未通过计。

## 2. 提交条件与判定

以下条件在提交阶段统一判定。此处不作资格取消，各条未满足时的处理方式分别列出。

| #   | 条件                                                                       | 判定方式                  | 未满足时的处理                   |
| --- | -------------------------------------------------------------------------- | ------------------------- | -------------------------------- |
| 2.1 | 方案基于官方基础镜像构建，可独立重建，且能由赛事方在自有环境中复现运行     | 依 `Dockerfile` 重建并试运行 | 全部运行类得分无法产生        |
| 2.2 | 单卡运行，显存占用不超过 32 GB                                             | 运行时显存采样            | 超限的运行不计入统计             |
| 2.3 | 断网运行                                                                   | 沙箱网络策略 + 出流量监测 | 检出外部连接者按 2.9 处理        |
| 2.4 | `MODEL.md` 声明模型来源、版本、量化方式与上下文配置。基线由赛事方提供（`example/baseline.py`），队伍不得改动 | 文档核查 + 基线试运行 | **增益项 40 分不得分** |
| 2.5 | 若经微调：微调权重已开源，训练数据来源已说明                               | 文档核查 + 链接可达性     | 增益项不得分                     |
| 2.6 | 提交智能体源码与技能包                                                     | 提交物核查                | 工程质量项 20 分不得分           |
| 2.7 | 运行期间 GPU 存在实际推理负载                                              | 运行时利用率采样          | 见 2.9                           |
| 2.8 | 提交设计报告，含失败分析                                                   | 提交物核查                | 工程质量项按缺失程度折算         |
| 2.9 | 未通过外部检索、硬编码答案或绕过模型的方式取得结果                         | 见 2.10                   | **该 track 成绩作废**      |

### 2.10 关于 2.9 的判定

本赛道的部分题目与公开基准同源，其参考答案可在网络上获得。以下三类做法与赛道目的相悖：

- **联网检索**：沙箱断网，出流量非零即为异常
- **硬编码答案**：将答案预置于技能包或智能体代码中
- **绕过模型**：以确定性脚本产出结果，模型调用不具实质作用

判定依据三项，任一项异常即进入人工复核：

| 依据           | 说明                                     |
| -------------- | ---------------------------------------- |
| 网络出流量     | 应为零                                   |
| GPU 利用率曲线 | 全程贴近零，说明未实际执行推理           |
| 产物与 trace   | 生成的代码与 `trace.jsonl` 中的工具调用记录对不上 |

**不分发评测题集是本项最有效的防线。** VerilogEval 的 156 道题及其参考实现在网络上
公开可得，且大概率已存在于模型的训练语料中；预置答案或针对已见题目调优的方案，在
未见题集上的得分通常会大幅下降。

### 2.11 关于确定性检查脚本

以确定性脚本做接口比对、语法预检、格式规整**不属于**绕过模型，这类工作本就应当由
脚本承担，也是技能包应有的内容。

界线在于：**产出的设计本身是否由模型生成。** 用脚本检查模型的输出是工程；用脚本
拼出答案而模型只是走个过场，是 2.9 第三类。

### 2.12 关于商用 LLM API

开发阶段使用商用 API 不受限制，赛事方不作追溯。

但决赛在断网沙箱中运行，`MODEL.md` 中声明的必须是可本地部署的开源权重。以商用 API
提交的方案在 2.1 与 2.3 两条上均不成立，全部运行类得分无法产生。

## 3. 评分公式

### 3.1 能力（30 分）

#### 3.1.1 题集

赛事方备有一套评测题集，**赛前不公开**，于评测窗口分发给决赛入围队伍。窗口内不得修改
方案代码、技能包或模型权重，提交材料的哈希须与作品提交阶段的方案包一致。题量与构成
于赛前公告。

开发阶段建议以 VerilogEval v2（`dataset_spec-to-rtl`，156 题）自测，实测结果写入
设计报告。本仓库的 `selftest/veval_import.py` 负责把它转成可判定的格式。

#### 3.1.2 分级判定

```
L1 可编译  →  L2 仿真通过  →  L3 可综合
```

| 级别            | 判定方式                                                              |
| --------------- | --------------------------------------------------------------------- |
| **L1 可编译**   | `xvlog` 分析与 `xelab` 详细描述通过                                   |
| **L2 仿真通过** | `xsim` 运行参考测试台，逐拍比对无差异（`Mismatches: 0`）              |
| **L3 可综合**   | 在 `xczu3eg-sbva484-1-e` 上 `synth_design` 产出网表且无 ERROR         |

**全部判定在 AMD Vivado 工具链上完成，不引入 iverilog、Verilator、Yosys 等第三方
工具，也不引入形式验证工具。** 逐级递进，未通过前一级不进入下一级。

其中「L2 仿真通过」即功能正确性。参考测试台同时例化参考实现与待测模块并逐拍比对
输出，因此该级判定的是待测模块在激励范围内与参考实现的行为一致性，而非仅指仿真过程
未报错。

**模块名与端口必须与题目给出的接口一致。** 参考测试台按具名端口例化待测模块，
端口名、方向或位宽不符将导致详细描述失败，该题计为 L0，其代价高于功能实现错误。

#### 3.1.3 计分

取该题所达到的最高级别，按下列系数折算：

| 级别        | 系数 |
| ----------- | ---: |
| L0 未通过   |    0 |
| L1 可编译   |  0.2 |
| L2 仿真通过 |  0.7 |
| L3 可综合   |  1.0 |

```
题集得分 = Σ(题目系数) / 评测题集题数
能力得分 = 30 × 题集得分
```

采用分级折算而非只认最高级，是因为「能编译但功能错」与「连编译都不过」在工程上属于
不同的失败，对智能体的改进方向亦有不同指示。

**L1 到 L2 的 0.5 是全表最大的一跳**，反映的是「代码能过工具」到「行为与参考实现
一致」这一步的实际难度；而 L2 到 L3 只有 0.3，因为逐拍比对通过的设计多数已可综合。

#### 3.1.4 pass@1 与 pass@5

每题独立生成 5 次，同时报 pass@1 与 pass@5，其中**计分采用 pass@1**，pass@5 作为
稳定性诊断单独列出，不计入总分。

pass@1 对应实际使用场景。若按 pass@5 计分，会激励以重复采样换取分数，而重复采样的
代价已由墙钟项另行计量。

#### 3.1.5 环境失败不计入

判定器会区分「参赛代码不行」与「环境或题目出了问题」。后者包括授权席位签不出
（`LICENSE_ERROR`）、授权档位不覆盖目标器件（`PART_NOT_LICENSED`）、题目自带的参考
实现或测试台本身有问题（`FIXTURE_ERROR`）。

**这类样本不计入平均分**，而不是按 0 分计。若某题全部采样都是环境失败，该题整体排除，
题集得分按实际计分的题数取平均，并在结果中标注排除了哪些。

单列此条的原因在于，这两种失败在工具侧均为静默失败。缺少席位时 `xsim` 照常退出 0，日志
里没有 "license" 字样，只是该有的结果行不见了。若不加区分，一次授权抖动会让整批样本
落到最低档，而参赛方无从察觉，也无从申诉。

### 3.2 增益（40 分）

以队伍所声明模型在**无智能体、无技能包、单次直接生成**条件下的结果为基线：

```
增益 = 方案题集得分 / 基线题集得分
```

**基线由赛事方提供，队伍不得改动。** 脚本是 `example/baseline.py`，其提示词、采样参数
（temperature 0）、单次不重试、不调用工具这几项全部固定。队伍能决定的是模型、量化方式
与推理后端，上述选择同样会体现在基线中，因为 `baseline.py` 所连接的即为队伍自行启动的推理
服务，与方案运行时是同一个。

这样定是因为基线是增益的**分母**：分母若由参赛方提供，把自己的基线做弱就能抬高增益，
而做弱基线比做强方案容易得多。固定基线之后，这一项衡量的才是"智能体与技能包带来了
多少提升"，而不是"基线被压得多低"。

基线须与方案在**同一次运行**中产出，不接受分次提交。评测产物里 `trace.jsonl` 的首行会
记录 `baseline.py` 自身的 SHA-256，用于核对分母确实出自赛事方那份脚本。

**满分线于赛前公布，采用固定倍数而非场内最优**，中间按对数比例给分：

```
Score = 40 × log(增益) / log(满分线倍数)        上限 40 分，下限 0 分
```

采用对数而非线性，是因为增益的边际难度随倍数递增：把 1.0 倍做到 1.5 倍与把 2.0 倍
做到 2.5 倍，工程量相差很大，线性给分会低估后者。

基线得分为零时，增益无从计算，本项按赛前公告的规则单独处理。

### 3.3 代价（10 分）

以完成全题集的墙钟时间计量：

```
Score = 10 × min(基准时长 / 实测时长, 1)
```

基准时长于赛前公布，快于基准者封顶 10 分，不另行奖励。

单题墙钟以**赛事方发出请求到收到响应**为准，队伍自报的 `elapsed_s` 不作数。

采用墙钟而非 token 计数，一是可在容器外观测，二是同一模型在不同推理后端下吞吐可相差
数倍，选择后端与调校服务配置本身即是应当考察的工程能力。

### 3.4 工程质量（20 分）

| 评定锚点                       | 说明                                                       |
| ------------------------------ | ---------------------------------------------------------- |
| 智能体设计的清晰程度           | 控制流、重试与回退策略是否说得清、是否有据                 |
| 技能包的可复用性               | 他人能否照着用；是否给出适用与不适用条件                   |
| `trace.jsonl` 的完整程度       | 每次工具调用是否可追溯                                     |
| 文档完整度                     | 一名工程人员能否据以理解并复现该方案                       |
| **失败分析的深度**       | 本项的重点，见下                                           |

失败分析要说清楚：哪一类题目仍然做不出来、原因是什么、曾尝试过什么、为什么无效。
**一份诚实且有归因的失败分析，得分高于一份只呈现成功案例的报告。**

技能包不必涉及大模型。确定性的校验脚本与结构化的踩坑清单同样计分，评价标准在于他人
能否复用。

### 3.5 两个 track 的处理

RTL 与 HLS 各自独立计分、独立排名、独立评奖，**推荐只选其一**。两个都做的队伍在两个
榜单上分别出现，不作合并计分，也不因多做一个 track 而获得加分；最终排名取两个 track
中较高的一个。

## 4. 评分示例

### 4.1 示例数据

假设某队伍参加 RTL track，评测题集共 30 题，每题生成 5 次取 pass@1。
**下表的题数与各级题目数均为便于说明的示例值，实际题量于赛前公告。**

| 达到级别       |         题数 | 系数 |           小计 |
| -------------- | -----------: | ---: | -------------: |
| L0 未通过      |            3 |    0 |            0.0 |
| L1 可编译      |            3 |  0.2 |            0.6 |
| L2 仿真通过    |            6 |  0.7 |            4.2 |
| L3 可综合      |           18 |  1.0 |           18.0 |
| **合计** | **30** |      | **22.8** |

```
题集得分 = 22.8 / 30 = 0.760
```

### 4.2 能力

```
能力 = 30 × 0.760 = 22.8 分
```

### 4.3 增益

```
基线（同模型直接生成）题集得分 = 0.380
增益 = 0.760 / 0.380 = 2.00 倍

设满分线为 2.5 倍：
Score = 40 × log(2.00) / log(2.5) = 40 × 0.693 / 0.916 = 30.3 分
```

增益取题集得分之比，与能力项的分值刻度无关。

### 4.4 代价

```
基准时长 6 小时，实测 7.5 小时
Score = 10 × min(6 / 7.5, 1) = 8.0 分
```

### 4.5 汇总

| 评测项         |           得分 |
| -------------- | -------------: |
| 能力           |      22.8 / 30 |
| 增益           |      30.3 / 40 |
| 代价           |       8.0 / 10 |
| 工程质量       |      15.0 / 20 |
| **总分** | **76.1** |

诊断项另行列示：pass@1 与 pass@5 的差值。

## 5. 提交要求与检查清单

### 5.1 方案包结构

```
<team_name>-agent/
├── Dockerfile              # 基于官方基础镜像构建
├── manifest.json           # 机器可读的方案声明
├── model/
│   └── MODEL.md            # 模型来源、版本、量化方式、显存占用实测、上下文配置
├── agent/                  # 智能体源码
├── skill/                  # 技能包
│   ├── README.md
│   └── <skill-name>/
├── serve/                  # 推理服务配置与启动脚本
├── run.sh                  # 单题入口：读题 → 产出代码
├── run_baseline.sh         # 赛事方提供，勿改；调用同目录的 baseline.py
├── baseline.py             # 赛事方提供，勿改；增益项的分母
└── REPORT.md               # 设计报告
```

仓库内所有目录名与文件名须使用纯英文，采用小写字母、数字、下划线或连字符，中文内容
仅出现于文件正文中。

本仓库的 [example/](./example/) 即按此结构编写，可直接作为起点。

### 5.2 `run.sh` 的接口契约

```
./run.sh <input_dir> <output_dir>
```

| 位置                        | 内容                                              |
| --------------------------- | ------------------------------------------------- |
| `<input_dir>/prompt.txt`    | 题面                                              |
| `<input_dir>/interface.txt` | **不提供**，接口写在题面里。示例题与之同形     |
| `<output_dir>/solution.v`   | 产出的 RTL 代码。做不出来写空文件，不要报错       |
| `<output_dir>/trace.jsonl`  | 工具调用记录，每行一个 JSON 对象                  |

`run_baseline.sh` 接口相同。

### 5.3 提交前检查清单

- [ ] `Dockerfile` 基于官方基础镜像，可在干净环境中重建
- [ ] `MODEL.md` 中声明的是**本地开源权重**，不是商用 API
- [ ] 实测单卡显存占用不超过 32 GB
- [ ] 断网条件下可完整运行，无外部依赖下载
- [ ] `MODEL.md` 已写明来源、版本号或校验和、量化方式、实测显存、上下文配置
- [ ] 若经微调：权重已开源，链接可达，训练数据来源已说明
- [ ] `run.sh` 可接受单题输入并产出 `solution.v`，无需人工介入
- [ ] `run_baseline.sh` 与 `baseline.py` 保持赛事方原样，未作改动
- [ ] 方案与基线在同一次运行中产出
- [ ] `trace.jsonl` 记录了每一次工具调用
- [ ] 单题运行时间在墙钟上限内
- [ ] 智能体源码与技能包齐全，技能包含 `README.md`
- [ ] 设计报告含模型选择理由、智能体设计说明与**失败分析**
- [ ] 已用 `selftest/` 在本地跑通一轮
- [ ] 目录名与文件名全为英文

### 5.4 赛前发布材料

- 基础镜像，gfx1100 与 gfx1201 两个版本
- 示范方案一份，含最小可用的智能体与技能包
- 本地自测脚本与示例题目
- VerilogEval 的 Vivado 版自测脚本
- 决赛环境技术公告
